# E5b′ 修正记录 2026-09-19

## 现象

smoke（source 6101，target 84001）在 H_init 区块报错退出：`model h0 differs from the H_init start states`。报错位置在核权重装入检查之后，说明两个核的装入都已通过。

## 根因

原检查用 `torch.allclose` 的默认容差（rtol 1e-5，atol 1e-8）逐元素比较两次独立的矩阵乘。参照值一次算 64 行，trajectory batch 一次算 128 行。GPU 上行数不同时 cuBLAS 可能换用不同的内核和求和顺序，结果在末位上有差异。ReLU 之后接近零的元素，相对容差几乎为零，只剩 1e-8 的绝对容差，末位差异就会判为不一致。CPU 上两次乘法走同一个 MKL 内核，结果逐位相同，所以本地测试没有暴露。

用真实模型在 CPU 上只改求和顺序复现：524,288 个元素中 870 个判为不一致，全部是接近零的元素；真实最大偏差只有起点状态最大值的 3.5e-7。去掉 ReLU 这类真正的公式错误，偏差是 1.0。

## 修改（只改 run_delta.py 的 init_block）

1. H_init 起点状态改为直接取模型自己前向输出的 `h0`，不再在脚本里重写一遍公式。
2. 一致性检查改为"最大偏差除以起点状态最大值"，容差 1e-4。它比舍入噪声大约 300 倍，比公式错误小约 1 万倍。
3. 实测最大偏差写入 COMPLETE.json 的 `h0_max_relative_deviation`。报错信息只含这个数字。

## 未改坏的证明

- AST 比对：`main`、`nav_block`、`nav_checkpoint`、`preflight`、`run_cell` 与修正前完全相同，只有 `init_block` 改动。
- 本地同一 cell 重跑：`delta.csv`、`trajectory_profile.csv`、`retention.csv` 与修正前逐字节相同；COMPLETE.json 只多出一个字段，CPU 上其值为 0。
- 故障注入：给 h0 加上起点状态最大值 1e-6 量级的扰动（约为实测舍入噪声的 3 倍），检查通过并记录 9.8e-7；把 h0 放大 1%，检查报错并给出偏差 9.76e-3。
